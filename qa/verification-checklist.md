# QuipBot setup verification checklist

Use `pass`, `fail`, `blocked`, or `not-applicable` for each item.

## Authority and connection

- Site ownership/management authority confirmed.
- Canonical HTTPS origin confirmed.
- WordPress Application Password stored outside the transcript.
- Connected user has only the required capability.
- Public setup API version is supported.

## Provider and data

- Provider and model match the approved plan.
- Provider status confirms a tested key without returning it.
- Knowledge facts match cited sources and owner decisions.
- No credential appears in local artifacts or logs.
- Retention and lead fields match the approved privacy decision.

## Behavior

- Supported questions receive grounded answers.
- Unsupported or high-risk claims are refused or escalated.
- Consent appears before visitor content is sent externally.
- AI disclosure and legal wording match the approved copy.
- Human handoff reaches the intended destination.
- Error and offline states are understandable.

## Launch

- Test conversations are excluded from customer reporting where promised.
- Widget appearance works at mobile and desktop sizes.
- Public widget stayed off during initial configuration.
- Explicit go-live approval is recorded.
- One post-launch public session passes without storing visitor personal data in
  the verification artifact.
